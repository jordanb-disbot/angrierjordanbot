# Dashboard foundation — Phase 24 remains incomplete

The dashboard has a private settings view generated from the Master Settings Schema, with live values read through the same ConfigService and Prisma adapters as the bot. Ordinary controls retain generated labels, ranges, choices, risk classifications and revision metadata. The shared draft engine and generated save/stage/preview/publish/history/rollback controls are implemented; mutations remain disabled unless deployment explicitly sets `AJ_DASHBOARD_ACCEPTED=true`. The acceptance flag remains false. Unauthenticated visitors see only a sign-in page. Database failure is reported as unavailable, never substituted with fixture state.

## Authentication boundary

- Discord authorization-code OAuth uses only `identify guilds` scopes. The callback is exactly `/api/auth/discord/callback`; redirects use the configured public origin, never a submitted return URL or Host header.
- Required deployment variables: `PUBLIC_DASHBOARD_URL`, `DISCORD_OAUTH_CALLBACK_URL`, `DISCORD_OAUTH_CLIENT_ID`, `DISCORD_OAUTH_CLIENT_SECRET`, `DISCORD_GUILD_ID`, `DASHBOARD_SESSION_SECRET`. Production requires HTTPS. A localhost HTTP exception exists only outside production. Secrets are neither returned nor logged.
- Five-minute encrypted state cookies bind login requests to callbacks. Successful or failed callbacks clear that cookie. Discord's one-use authorization code provides exchange replay protection.
- Sessions are AES-256-GCM encrypted and authenticated, bound to purpose, public origin and configured server. Secure deployments use host-only `__Host-` cookies with HttpOnly, Secure, SameSite=Lax and Path=/; sessions expire within 30 minutes or earlier token expiry. Refresh tokens are discarded. Secret rotation invalidates all cookies. Multi-instance deployments must share the same secret.
- Every private page/API read and attempted settings mutation queries Discord afresh for current server membership and current owner/Administrator permissions, then invokes shared PermissionEngine `dashboard.access`. No Chairs hierarchy role, local whitelist or stale session claim grants access. Provider errors/rate limits fail closed. Guild pagination is bounded and fails closed if no authorized configured server is found.
- Writes require the exact Origin and session-bound CSRF token. Logout also requires CSRF, clears the cookie and attempts provider token revocation. A revocation failure reports local logout only; a copied cookie can remain usable until its short expiry. Logout works after permission removal because it grants no access to server state.
- Private API responses are no-store; private pages are dynamically rendered. Frame embedding is denied. Response bodies do not disclose provider errors, tokens or configuration values on authentication failures.

OAuth follows Discord's [OAuth2 documentation](https://github.com/discord/discord-api-docs/blob/main/developers/topics/oauth2.mdx) and [current member/server endpoints](https://github.com/discord/discord-api-docs/blob/main/developers/resources/user.mdx). Tests use fake tokens and injected fetch responses; no real OAuth calls or credentials were used for validation.

## Shared configuration transactions and drafts

Prisma-backed ConfigService writes now commit settings, revision history and audit together. All config mutations and draft operations use the same server-scoped PostgreSQL transaction lock, including initially absent/default values. Dashboard operations additionally persist an existing OperationReceipt with actor/command fingerprint. Exact retries return their committed result, including after restart; altered requests cannot reuse the receipt. The legacy in-memory ConfigService adapter remains compatible but is never used by dashboard routes.

Migration `0015_dashboard_drafts` adds one DashboardDraft row per configured server, shared across all sections. One Admin holds the edit lock; edits and explicit renewal refresh its 15-minute inactivity timer. Read-only views do not renew it. Only the current owner may forcibly take over, with before/after audit. Every edit requires an expected draft revision. Any current Admin may manually publish a valid reviewed draft. Settings/revisions, draft state, audits and receipt commit or roll back together.

Preview freezes before/after values, setting versions, schema rules, current direct dependencies and applicable current Discord object references in a fingerprint. Publish recomputes the fingerprint and validation under the same transaction lock; changed values, metadata, dependencies or references require a fresh preview. Dependency display includes only immediate relationships, without transitive expansion or automatic repair. Unsupported complex JSON editors remain blocked. Primitive ranges/choices/types, known repair min/max, solo reward/cap and spotlight-window relationships are enforced. Enabled features require valid declared direct prerequisites. Built-in notification-role maps reuse the Special Commands shared validator, and live role verification reuses its unmanaged/zero-permission opt-in role rule; enabling Line requires a configured safe notification role. The role-map UI editor remains pending even though shared validation supports the map. Channel/role references are verified from Discord immediately during preview and publish; this requires server-side `DISCORD_TOKEN`, and missing credentials/provider failures block the affected draft. Reference verification does not create, delete or repair Discord objects.

Only explicit schema `dashboard_write: live`, normal-risk primitives with no direct dependency relationships may save live. High-impact/financial/security settings require the draft even if client metadata is altered. Rollback stages a retained rollback-safe configuration revision for the same preview/publish path; it creates a new config revision and new audit entry. Both history and rollback enforce the canonical 365-day window. No scheduled publish path exists. `/api/draft` is the sole mutation API; `/api/settings` does not provide a bypass.

## Explicitly unfinished

Production mutations remain blocked with `423 DASHBOARD_READ_ONLY` until dashboard acceptance. There is no development/test environment override for this gate. Offline and disposable PostgreSQL tests call the shared engine directly.

Remaining Phase 24 work includes dedicated launch page workflows, role-panel/object lifecycle management, Special Commands/custom commands and other complex JSON editors, content/tutorial editors, audit screens/export and rolling audit-retention job, user management, full status screens, and destructive Discord-object impact/rollback behavior. The current primitive settings preview is not a complete destructive-object preview. Authenticated live-browser/OAuth acceptance and actual desktop/mobile functional walkthroughs remain pending. This increment is not Gate D acceptance, and `AJ_DASHBOARD_ACCEPTED` remains false.
