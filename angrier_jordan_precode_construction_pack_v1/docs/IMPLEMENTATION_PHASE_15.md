# Phase 15 — Direct PvP skill games

Implements `/game tictactoe`, `/game connectfour`, and `/game battleship` with the existing required member and optional wager options. Free is the default. `features.pvp` stays disabled until acceptance. Shared `pvp.play` capability, current member eligibility/channel permissions, and `channels.games_channel` guard every interaction; both members are freshly checked at challenge, acceptance, and replay.

Challenges expire after two minutes, reserve nothing before acceptance, and allow challenger cancellation or opponent decline. Acceptance validates both matching stakes against current settings/balances and reserves both atomically through the shared ledger/escrow. Any insufficient balance rolls the entire transaction back. One active challenge/match per member spans all three games and channels. Five-minute turns end by timeout forfeit. Confirmed forfeits and wins award the complete pot, without rake; draws return exact wallet/bank funding sources. Game-specific and combined `skill_games` statistics commit with settlement.

Tic-Tac-Toe uses a 3×3 board. Connect Four uses seven columns, six rows and gravity. Battleship uses standard 10×10 boards and five straight ships of lengths 5/4/3/3/2; overlap is rejected, touching is allowed. The challenger places first, followed by the opponent, each with a five-minute placement turn. Each chooses Auto Place or Place Manually using coordinate ranges. Combat starts only when both fleets are valid; shots alternate, including after hits. This uses ordinary board parameters where the canonical contract delegates standard movement rules.

Battleship fleets are stored only in each `GameParticipant.data`, outside public `GameSession.data`. Public output includes placement readiness and resolved shots, never unhit fleet cells. The private projection authenticates server, channel and participant and selects only that member’s fleet. Own-board interactions and placement/fire modals are ephemeral and actor-bound; public renderers only accept the explicit public projection. Completed results do not reveal opposing fleets.

Play Again creates a new challenge for the same opponent, preserves the previous match, and carries the explicitly displayed stake as a proposal. It reserves no money until fresh opponent acceptance and balance/limit revalidation. Old controls are version-bound. Durable operation receipts reject mismatched replay; transaction-scoped SessionEngine, TimerEngine, ledger and escrow services own all consequential state transitions. Persisted `pvp.expire` jobs contain session version; stale jobs do nothing, and worker restart/sweep converges on the authoritative deadline. No new schema/migration is needed.

Rendering uses the frozen shared event shell, panels and Space Grotesk/Inter typography. No runtime AI assets or new visual system. Public publication failure cancels only an unfunded challenge; accepted matches remain persisted for financial recovery. Dashboard settings are `pvp.min_wager` and `pvp.max_wager`; timing is canonical and not editable.

Verification coverage: domain wins/draws/turns/gravity/fleet geometry; PostgreSQL concurrent challenge locks, acceptance/cancellation, double acceptance, insufficient second-side funding rollback, stale/foreign controls, final-move settlement, source-correct refunds, replay, fleet privacy and restart/duplicate-worker timeout payout. Adapter tests cover disabled/channel/eligibility guards, participant privacy and permanent visual frame.
