# Phase 20 — community

All runtime entry points remain behind `features.community=false` until acceptance. No production Discord, credentials or deployments are used for implementation verification.

The shared serializable operation runner commits sessions, ballots, mirrors, scheduled jobs, audit and Ledger/escrow effects together. Existing community tables are sufficient; this phase requires no schema migration. `community.advance` owns timed phase transitions and `community.publish` owns both initial delivery and persisted state refresh. All initial publication attempts share the version-zero DeliveryEngine intent, including later refresh jobs arriving before the first message links. Anonymous projections exclude private ballot/nomination identities, submitters and deterministic tie seeds.

`/poll` accepts 2–25 pipe-separated choices within `poll.max_choices` (default 20), optional 1-minute–7-day duration, manual close by creator/community admin, hidden/live totals, anonymous/named ballots and ranked-choice. Ranked ballots store one ordered array per member and use shared Voting validation/tallies at each instant-runoff round. Partial ballots exhaust; deterministic seeded elimination resolves tied cutoffs. The last saved ballot counts. Named ballots are exposed only under the selected result visibility rule.

`/superlatives categories:` is Chaise Lounge/Throne only. Omission locates the active season. Seasons number per server; only one season can remain active. Nominations last 48 hours, allow one immutable nomination per member/category and reject self-nominations. Top five per category are ordered by nomination count with a saved deterministic tie seed. Voting receives a full 48 hours after transition recovery; repeated advancement does not reopen or extend it. Each nominated category receives one final winner with deterministic tie resolution, including a no-vote final. Categories without nominations have no winner and state that explicitly. Winners receive permanent season/category achievements; no Ottomans. Only phase-transition publication is scheduled, avoiding repetitive reminder pings.

`/suggest` submits named/anonymous suggestions or searches a paginated archive. Support/Oppose use one revisable ballot. Shared community.manage authority updates OPEN/REVIEWING/ACCEPTED/DECLINED/IMPLEMENTED with an audit event. `/ama` similarly submits questions; only upvotes are available. Admin answers/declines, answers publish, and decline replaces the public question with a tombstone. The submitter's private archive retains the question and status; other members cannot find declined questions. Admins can sort by upvotes. Both archives expose twenty entries per selectable page.

`/giveaway` creation requires shared community.manage (Chaise Lounge/Throne). Duration is 1h–7d, 1–5 winners, free or a configured bounded fee (`giveaway.max_entry_fee`, default 100, hard ceiling 5000 matching the established economy wager ceiling). A private exact-fee confirmation precedes entry. Concurrent/replayed entry cannot charge twice. Fees reserve through shared escrow, then settle with zero refund/payout to remove them from circulation. They do not fund prizes. The saved draw seed deterministically picks distinct entrants; fewer entrants means fewer winners. Ottoman rewards use Ledger, catalog rewards reuse `grantCatalogReward` (real tool instances/recipe ownership/collection discoveries), direct recipes grant ownership, and custom rewards remain explicitly FULFILLMENT_PENDING until an audited staff action acknowledges delivery. Catalog reward definitions are snapshotted at creation so later catalog disablement cannot strand an already promised prize.

The deterministic renderer uses the frozen Gate A lounge shell and Space Grotesk/Inter typography. `renderCommunity(publicView)` renders the same layout the coordinator sends. `superlativeReviewFixture()` is a labeled review-only saved-state fixture for Gate B; fixture names are not live member records. `communityTranscript` provides the full content when the card is truncated.

Validation: runtime domain, Discord adapter and disposable-schema PostgreSQL tests cover visibility, permissions, server/channel/message bindings, ranked ballots, one-time nominations, concurrent season/entry/settlement, restart transition timing, badges, catalog grants, held-wallet restrictions, audit and queued publication. Execution results belong in the root implementation status once run. Real Discord delivery/readability acceptance and Gate B owner review remain pending.
