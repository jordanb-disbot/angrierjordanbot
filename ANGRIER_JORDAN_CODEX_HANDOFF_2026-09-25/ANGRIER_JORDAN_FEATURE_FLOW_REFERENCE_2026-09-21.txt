GLOBAL RULES THAT APPLY TO ALL FLOWS
- Bot display name: Angrier Jordan.
- Bot Discord role: The Chairman.
- Human hierarchy: Throne > Chaise Lounge > Recliner.
- User-facing language says server/member, not guild, except internal Discord/API code may still use guild identifiers.
- Discord IDs/role IDs, not display names, are authoritative for permissions.
- Important financial/social timers are persisted and restart-safe.
- Currency/inventory movement is transactional, idempotent, and ledger-backed.
- Wagers and auctions use escrow before settlement.
- Feature flags can disable modules without deleting stored member data.
- Moderation-Hotseat members cannot bypass restrictions with stale buttons or components.
- Runtime visuals are deterministic templates using real Discord/database state; AI image generation is not used during normal runtime.
- The approved visual system is the dark Discord-native Angrier Jordan/Chairs style with navy, teal/emerald, gold, readable typography, and feature-specific accent variation.

======================================================================
1. SERVER SETUP AND HEALTH
======================================================================

Commands: /setup, /setup health

Purpose:
Initialize and validate the one-server Angrier Jordan installation.

Flow:
1. An authorized owner/admin starts /setup.
2. Angrier Jordan validates required server configuration, mapped channels, mapped roles, role hierarchy, and enabled-module permissions.
3. The bot checks that The Chairman can manage the roles/members/channels required by enabled features.
4. The bot identifies missing or unsafe configuration instead of silently pretending the feature will work.
5. Configuration is saved through the shared configuration service/database, not by editing deployed JSON.
6. /setup health can be used later to re-run configuration and capability checks.
7. Health output is private/ephemeral and lists actionable problems.

End state:
The server has a validated configuration baseline. Features with unmet requirements remain safely unavailable rather than partially functioning.

2. RULES AND ONBOARDING
======================================================================

Command: /rules
Related optional next steps: /roles, /lore, /introduce, /tutorial

Purpose:
Make server-rules acknowledgment the only mandatory onboarding gate.

New-member flow:
1. A new member joins.
2. Angrier Jordan presents or makes available the rules acknowledgment experience.
3. The member reads the rules and acknowledges them.
4. Angrier Jordan checks whether the member has an active punishment that must be restored.
5. If there is no active punishment, Angrier Jordan grants the configured normal member/access role.
6. If there is an active punishment, the punishment state is restored instead of normal member access.
7. The member is offered /roles, /lore, /introduce, and /tutorial as optional/skippable next steps.
8. Those optional features remain available permanently after onboarding.

Rejoin flow:
1. A former member rejoins.
2. The member must acknowledge rules again before normal access is restored.
3. Persistent Angrier Jordan data remains intact: profile, economy, inventory, collections, family/social state, achievements, game records, privacy, cosmetics, and showcase state.
4. Eligible prior self-selected roles and eligible non-staff manual/custom roles are restored when the Discord role still exists and Angrier Jordan can assign it.
5. Staff roles are never auto-restored; current staff must reapprove them.
6. Booster/Nitro roles are determined by Discord's current boost state.
7. Temporary roles keep aging while the member is gone and are restored only if still valid.
8. The old server nickname is restored when permissions allow.
9. Restoration failures are logged but do not block the member from rejoining.

Punishment-on-rejoin flow:
1. If the member left with an active punishment, that state persists.
2. Finite punishment time pauses while the member is absent.
3. The member acknowledges rules after returning.
4. The remaining punishment is resumed and the Jailed/restricted state is applied.
5. Normal access is restored only when the punishment independently ends.

3. SELF-SELECT ROLES
======================================================================

Command: /roles

Purpose:
Give members one private role-selection panel with no administrative controls.

Member flow:
1. Member runs /roles.
2. Angrier Jordan opens one ephemeral/private role panel.
3. Categories appear in configured order: Gender, Age, Regions, Vices, Personalities, Pings, DM Status.
4. Existing selections are preselected.
5. Gender, Age, Regions, and DM Status are single-choice but clearable.
6. Selecting a new option in a single-choice category removes the previous option immediately.
7. Vices and Personalities are multi-select with no product-level cap; Discord-safe menus may be split internally if needed.
8. Pings are independent multi-select roles, including Line, Race, Chess, and VC.
9. Every change applies immediately; there is no Save button.
10. Angrier Jordan refuses to assign mapped roles that have Discord permissions, are managed, are above the bot's manageable hierarchy, or otherwise fail safety checks.

Dashboard archive/restore flow:
1. Admin archives/disables a role option in the dashboard.
2. The option disappears from /roles immediately.
3. The underlying role is removed from current holders.
4. Angrier Jordan remembers which eligible members held it.
5. Admin later re-enables the option.
6. Angrier Jordan automatically restores the role to prior holders who are still eligible.

Option delete flow:
1. Admin deletes one role option.
2. The role is removed from members.
3. The underlying Discord role is deleted.
4. Mappings/configuration are removed.
5. The action is audited.

Category delete flow:
1. Admin selects category deletion.
2. Because this is destructive, explicit confirmation is required.
3. All roles belonging to that category are removed from members.
4. Underlying Discord roles and mappings are deleted.
5. The action is audited.

4. HELP AND INTERACTIVE TUTORIAL
======================================================================

Commands: /help, /tutorial and tutorial subflows

/help flow:
1. Member runs /help or searches for a command.
2. Angrier Jordan filters results to commands/features that member is actually authorized to see.
3. It shows the exact current command path, not a retired alias.
4. It explains command purpose, required/optional fields, and at least one complete example.
5. Complex commands expose Walk Me Through It / contextual help when a tutorial exists.
6. Enabled Special Commands (!line, !race, !vc, !chess, plus authorized custom Special Commands) appear in help where relevant.

/tutorial flow:
1. Member opens /tutorial or a Show Me Around / How This Works entry point.
2. Angrier Jordan shows permission-appropriate tutorial paths.
3. Member selects a path or specific command lesson.
4. Each lesson presents a short purpose, 2-5 steps, relevant commands, field explanations, and an example.
5. Practice is offered when it can be simulated safely.
6. Practice mode never changes real balances, roles, wagers, moderation state, security state, or other protected data.
7. Progress is stored privately with stable lesson IDs.
8. Member may continue, inspect progress, restart a path, or exit.
9. Tutorial completion gives no Ottomans, badge, or gameplay progression reward.

7. PROFILE, SHOWCASE, ACTIVITY, AND PRIVACY
======================================================================

Commands: /profile, /privacy activity, /privacy roast
No standalone /showcase command.

/profile flow:
1. Member opens /profile.
2. The public profile renders available member statistics and progression, including game records, achievements, collections, Chair Building rank, family counters, gifting/work stats, wanted status, and Weekly Spotlight area.
3. Activity metrics may show month/all-time messages, words, VC time, most-used word, and most-used bot command when activity privacy is visible.
4. Member may use Edit Showcase privately from the profile.
5. Edit Showcase lets the member choose allowed featured collectibles/badges/cosmetic presentation.
6. Changes update the stored profile/showcase state.
7. There is no separate /showcase slash command.

/privacy activity flow:
1. Member opens /privacy activity.
2. The member toggles one global activity-visibility setting.
3. Hidden mode hides message count, word count, VC time, most-used word, and most-used command from routine profile display.
4. Game/economy/achievement/collection/record statistics stay public.
5. Weekly award-winning totals remain public in Weekly Spotlight announcements even when routine activity stats are hidden.

/privacy roast flow:
1. Member opens /privacy roast.
2. Member enables or disables being targeted by /social roast.
3. The preference is persisted and checked before a roast target is accepted.

Passive activity-tracking flow:
1. Angrier Jordan observes qualifying main/community activity.
2. Bot messages, commands, bot/game/staff channels, URL-only, mention-only, and emoji-only messages are excluded from profile message/word counts.
3. Qualifying messages increment message count.
4. Natural-language words are counted after stripping URLs/mentions/standalone emoji tokens.
5. Stop words count toward total words but are excluded from most-used-word ranking.
6. VC time counts only in non-AFK voice, with at least one other non-bot member present, and while the member is not self-muted or self-deafened.
7. Monthly and all-time counters are maintained separately.

8. WEEKLY SPOTLIGHT
======================================================================

Passive weekly feature.
Badges: The Loudest Chair, The Wordsmith, Voice of the Lounge, Triple Threat.

Flow:
1. The weekly measurement period runs until Monday 4:00 AM Mountain Time.
2. Angrier Jordan freezes qualifying statistics for the completed week.
3. It determines co-winners for most qualifying messages, most qualifying words, and most qualifying VC time.
4. Ties produce co-winners; each receives the active rotating badge and historical win credit.
5. If one member holds all three titles in the same weekly result, Triple Threat unlocks permanently.
6. Once Triple Threat is earned, it permanently occupies that premium profile showcase slot even though future weekly wins still increment historical counters.
7. Angrier Jordan builds one Weekly Spotlight announcement for main chat beginning with @everyone.
8. The announcement uses actual avatars/names, winning totals, lifetime category wins, status labels, and server totals.
9. The result is posted during a learned high-engagement Monday evening window, approximately 5-10 PM MT, with 7 PM fallback if history is insufficient.
10. Only one announcement is sent per weekly result.

10. OTTOMAN WALLET, BANK, TRANSFERS, AND STATEMENT
======================================================================

Commands: /statement, /bank, /transfer
Currency: Ottomans
Balances: Wallet + Bank

Starter balance flow:
1. New eligible member account is initialized.
2. A small one-time starter balance is granted.
3. starterGrantedAt prevents duplicate starter grants after rejoin/bootstrap retries.

Spending rule:
1. A feature requests an Ottoman charge.
2. The ledger spends from Wallet first.
3. If Wallet is insufficient, the remainder is pulled from Bank.
4. If combined funds are insufficient, the transaction fails without moving funds.
5. Idempotency keys prevent duplicate interaction settlement.

/bank flow:
1. Member opens /bank.
2. Angrier Jordan shows wallet/bank state, current bank tier/capacity, and available bank actions.
3. Wallet-bank transfers are immediate and free.
4. Bank upgrades are offered under current tier rules.
5. For tiers 1-4, the current tier must be full before the upgrade charge can be applied.
6. Upgrade charge uses the normal wallet-first spending rule.
7. Tier 5 is the top tier and is unlimited.
8. Tier 5 interest posts Monday 4:00 AM MT, once per weekly cycle, within configured basis-point and payout caps.

/transfer flow:
1. Member selects another eligible member and Ottoman amount.
2. Self-transfer or invalid targets are rejected where nonsensical.
3. Balance and restrictions are validated.
4. Sender pays wallet first, then bank remainder if needed.
5. Recipient receives the funds in Wallet.
6. Direct member transfers have no fee.
7. The ledger records both sides atomically.

/statement flow:
1. Member runs /statement.
2. Bot displays wallet, bank, liquid net worth, and recent transactions/reasons.
3. Internal accounting remains more detailed than the member-facing statement.

Hidden economy balancing flow:
1. Angrier Jordan monitors aggregate wealth/distribution, shop spend, sell volume, casino, and bank growth.
2. Within hard bounds, it may gradually tune safe configuration values such as work payouts, loot sell values, shop prices, bet limits, odds, and drop rates.
3. It does not show members an economy-state meter or price-history feed.
4. Rare-item prestige is protected; corrections are gradual rather than sudden.

11. DAILY HUB
======================================================================

Command: /daily
Standalone /spin and /fortune do not exist.
Reset: 4:00 AM Mountain Time.

Flow:
1. Member runs /daily.
2. Angrier Jordan opens a private/ephemeral hub.
3. The hub shows Claim Daily, Daily Spin, and Fortune with used/available state for the current cycle.
4. Member chooses one action.
5. The bot revalidates that action has not already been used this cycle.
6. The selected action resolves.
7. Only that action becomes unavailable until reset; the other daily actions remain usable if not claimed.

Claim Daily:
1. Guaranteed Ottoman reward is granted.
2. Streak is checked against the immediately prior daily cycle.
3. Missing a cycle resets the streak to 1.
4. Milestone rewards are evaluated at 7, 30, 100, and 365 days.

Daily Spin:
1. Bot rolls once against the configured weighted table.
2. Reward may be Ottomans, junk, sellables, tools, mystery boxes, rare collectibles, or other bounded configured rewards.
3. Reward is settled atomically.
4. Extra spins cannot be purchased.

Fortune:
1. Bot selects one authored fortune/effect from the fortune bank.
2. It presents the fortune with Angrier Jordan flavor.
3. Small effects/items/rare surprises may occur within economy bounds.

13. REPEATABLE GRIND
======================================================================

Commands: /work, /fish, /dig, /scavenge

Shared flow:
1. Member invokes an activity.
2. Technical anti-spam/idempotency checks run; there is no gameplay cooldown for the basic grind commands.
3. Tool requirements are checked where applicable.
4. Activity outcome is rolled from configured bounded tables.
5. Ottoman/item/tool-durability effects are applied atomically.
6. Negative outcomes can never drive combined liquid balances below zero.
7. Activity lifetime statistics are updated.

/work:
1. Requires no tool.
2. Pays Ottomans only; the runtime rejects item-drop configuration for /work.
3. Outcomes may be positive, zero, small loss/fine, or workshop-tool damage.
4. There is no /work jackpot.

/fish:
1. Requires an equipped usable fishing rod.
2. If equipped rod is broken, it auto-unequips and the best usable same-slot fallback is equipped if available.
3. With no usable rod, fishing is blocked.
4. Outcome may include configured Ottomans/items and durability change.

/dig:
Same structure as /fish, using the shovel slot.

/scavenge:
Same structure as /fish, using the scavenging-tool slot.

19. CHAIR BUILDING / CRAFTING
======================================================================

Command: /craft
Progression: Folding Chair -> Barstool -> Recliner -> Chaise Lounge -> Throne.
Ranks: Apprentice -> Craftsman -> Chairwright -> Master Chairwright -> Grand Chairwright.
Quality: Standard -> Fine -> Exceptional -> Masterwork -> Perfect.

Flow:
1. Member opens /craft.
2. Bot shows recipes the account owns and currently meets prerequisites for.
3. Recipe ownership, not rank alone, gates access.
4. Member selects recipe.
5. Bot validates recipe ownership, required materials, any prior crafted-chair input, workshop tool, and other prerequisites.
6. Materials are reserved/consumed under a transactional craft attempt.
7. Success/failure and quality are resolved using skill rank, recipe rules, and tool modifiers.
8. On success, the crafted chair is created as a permanent collectible with rolled quality.
9. On failure, some materials are consumed, skill progress still increases, and scrap may be produced.
10. Perfect quality is impossible at lower ranks, tiny at Master, and highest at Grand.
11. The visible rank changes when hidden skill thresholds are crossed; there is no numeric progress bar.
12. Duplicates are allowed and sellable.
13. Higher recipes may consume an earlier crafted chair.

Rare bot crafting orders may exist, but cooperative/hired-player crafting does not.

20. CASINO - SHARED RULES
======================================================================

Commands: /casino blackjack, /casino roulette, /casino slots, /casino dice, /casino coinflip

Shared flow:
1. Member starts a casino game and chooses the required wager/options.
2. Bot validates balance, min/max bet, jail/security restrictions, and feature availability.
3. Wager is committed through the ledger/escrow-safe casino path.
4. Game resolves using code-controlled RNG and the game's rules.
5. Payout/loss settles atomically in Ottomans only.
6. Statistics/records update.
7. Completed result card offers Play Again.
8. Play Again creates a new round; it may reuse the previous wager/secondary selection by default, but balance/limits/eligibility are revalidated before money is committed.
9. If the previous option is no longer valid, the bot opens/returns the appropriate selector instead of silently substituting.

Blackjack:
1. Wager is validated.
2. Cards are dealt under standard blackjack rules.
3. Member may Hit or Stand, and may Double or Split when legal.
4. Hand(s) resolve against the house.
5. Result and payout settle.
6. Play Again starts a fresh hand.

Roulette:
1. Member chooses wager and a supported roulette table selection.
2. Bet is validated/committed.
3. Roulette result is rolled.
4. Winning selection is compared to the member's bet.
5. Payout/loss settles.
6. Play Again may preserve the prior wager/selection after revalidation.
Note: the canonical sources lock the roulette feature but do not enumerate the final roulette bet-menu catalog in this document.

Slots:
1. Member chooses a supported wager size.
2. A small configured portion of qualifying bets contributes to the persistent Chair Pot.
3. Three chair-symbol reels resolve.
4. Ordinary combinations pay according to the slot table.
5. The ultra-rare matching-chair combination triggers Chair Pot.
6. Chair Pot jackpot result is public and may set casino records.
7. Play Again starts a new spin after normal validation.

Dice:
1. Member chooses wager and the offered dice choice/mode.
2. Bet is validated/committed.
3. Bot-vs-player dice result is rolled.
4. Outcome settles.
5. Play Again may preserve harmless prior choices after validation.
Note: the exact final dice choice catalog is not specified in the canonical source excerpt and should stay data/config driven.

Coinflip:
1. Member chooses Heads or Tails and wager.
2. Bet is validated/committed.
3. Coin result is rolled.
4. Win/loss settles.
5. Play Again may reuse the prior side and wager after validation.

21. WEEKLY LOTTERY AND CHAIR POT
======================================================================

Command: /lottery
Draw: Friday 8:00 PM Mountain Time.

Lottery purchase flow:
1. Member opens /lottery.
2. Bot shows current ticket price, ticket count, pot, and member's weekly count.
3. Member chooses ticket quantity up to the 20-ticket/member/week cap.

3. If tickets exist, one winner is selected fairly from ticket entries.
4. The winner receives the full ticket-funded pot.
5. There is no rake and no system-funded rollover.
6. A public branded result is posted and records update.
7. Lottery has no Play Again button because it is a scheduled weekly event.

Chair Pot flow is part of Slots:
1. Qualifying slot bets add a small configured contribution.
2. Pot persists server-wide.
3. Ultra-rare required slot result triggers the jackpot.
4. Jackpot settles atomically and posts a major public result.

23. CHAIR RACE
======================================================================

Trigger: !race
Retired: /race
Channel: main chat
Participants: 2-6 racers
Betting/entry window: 60 seconds, one host +30-second extension.

Flow:
1. Member types !race.
2. Trigger message is deleted.
3. Permission restrictions are checked; unauthorized triggers are deleted silently.
4. Angrier Jordan posts a randomized Race callout, pings the configured opt-in Race role, and opens the native Race card.
5. Starter automatically becomes Racer #1.
6. Other members use Join Race first-come/first-served until six racers or entry lock.
7. Each racer gets a distinct temporary race-chair visual; visuals never affect real odds.
8. The same initial 60-second timer covers BOTH racer entry and betting.
9. Host may use +30 Seconds once, extending BOTH entry and betting to 90 seconds maximum.
10. If all six racer slots fill, entry closes but betting continues until the active timer ends.
11. Bettor selects a racer from the public card.
12. Discord opens a private wager modal.
13. Bettor enters Ottoman amount.
14. Bot validates balance, limits, eligibility, and event state.
15. On confirmation, wager is committed and the one authoritative public Race card updates.
16. One racer selection per member per event; selection cannot switch after commitment.
17. Wager may be increased while betting is open and within limits.
18. Racers are allowed to bet.
19. If fewer than two racers exist at close, event cancels and all wagers refund safely.

Shared trigger flow:
1. Member sends the trigger.
2. Bot checks whether it is enabled and whether member is allowed by configured role restrictions.
3. If unauthorized, original trigger is deleted silently.
4. If authorized, original trigger is deleted.
5. Bot chooses a randomized authored Angrier Jordan response from the configured pool.
6. Bot mentions the configured opt-in notification role.
7. For !line, native Line Time state machine starts.
8. For !race, native Chair Race state machine starts.
9. !vc posts only the voice invitation/notification flow.
10. !chess posts only the chess challenge/notification flow; it is not an Angrier Jordan chess engine.

Dashboard-created Special Commands:
1. Admin defines !trigger, notification role, randomized response pool, enabled state, and allowed roles.
2. Member uses trigger.
3. Same authorization/deletion behavior runs.
4. Bot sends the configured notification/message.
5. Custom Special Commands cannot launch or impersonate native Race/Line state machines.

54. SAFE CUSTOM COMMAND BUILDER
======================================================================

Commands: /custom-command create, edit, delete, enable, disable, list, test, clone, info
Primary management: Admin dashboard.

Creation flow:
1. Authorized staff opens builder.
2. Selects supported trigger type: exact, prefix, bounded contains, safe-regex, or approved native shortcut/alias.
3. Selects safe conditions and one or more supported actions.
4. Supported actions include send/reply/DM bot text/cards, configured reactions, bounded delete-trigger behavior, safe add/remove/toggle of allowlisted self roles, show role panel, approved workflow delegation, randomized response pools, and validated variables.
5. Bot validates regex/action count/execution-time/response-size limits, role allowlist, hierarchy, and recursion rules.
6. Command is saved to database/configuration state and mutation is audited.
7. /custom-command test runs it in a safe test context.
8. Enable/disable controls whether it can fire.

Execution flow:
1. Incoming trigger matches a configured command.
2. Bot rechecks member/channel permissions, Hotseat/security restrictions, and current role hierarchy.
3. Bot executes only allowed actions.
4. Native Race/Line/economy/moderation state machines are never duplicated inside custom commands; approved delegation calls the native workflow.

Hard prohibitions:
- No arbitrary JavaScript/Go templates/shell/SQL.
- No arbitrary HTTP callbacks in v1.
- No recursive custom-command loops.
- No secrets/environment access.
- No assignment of protected/staff/bot-managed roles through generic role actions.

59. MANUAL MODERATION
======================================================================

Commands: /mod warn, timeout, untimeout, kick, ban, unban, purge, note, history, case view, case edit, case reverse, lock, unlock, slowmode, quarantine, staff-alert, modstats

Shared punitive action flow:
1. Staff runs the action with required fields/reason.
2. Bot checks staff capability, target protection, Discord hierarchy, and whether The Chairman can perform the action.
3. For case-producing actions, a permanent numbered case is prepared before Discord enforcement.
4. Bot sends the Discord moderation action.
5. Bot does not report success until Discord confirms the external action.
6. If Discord enforcement fails, case remains with an enforcement-failed/reversed transition rather than falsely recording success.
7. Successful action records transition/audit history.
8. Where appropriate, affected member receives private explanation with action, policy category, duration, case ID, and Request Review.
9. Staff/security log receives the event.

/mod warn:
- Creates a documented warning case.
- Reversal can mark warning case reversed.

/mod timeout:
- Supports Discord timeout from 10 seconds through 28 days.
- Temporary expiry is persisted/restart-safe.
- Case remains auditable after expiry.

/mod untimeout:
- Ends an active timeout early when authorized and records the reason.

/mod kick:
- Removes member without banning rejoin.
- Kick cannot be automatically reversed because Discord cannot restore a kicked member.

/mod ban:
- Supports temporary ban from 1 minute through 365 days and permanent ban.
- Optional bounded recent-message deletion window may be used.
- Temporary unban job is persisted/restart-safe.

/mod unban:
- Removes an existing ban using Discord user ID and reason.

/mod purge:
1. Staff chooses bounded count and optional member/content filter plus required reason.
2. Bot validates API constraints.
3. Eligible messages are deleted.
4. Action/case/audit record is created as appropriate.
5. Deleted messages are not automatically reversible.

/mod note:
- Adds relevant staff-only note to member moderation history; never shown to member.

/mod history:
- Searches/returns member moderation history under staff permissions.

/mod case view:
- Shows numbered case, action, subject, reason, actor, timestamps, evidence refs, status, edits, and appeal history.

/mod case edit:
- Corrects permitted case reason/metadata while preserving before/after audit history.

/mod case reverse:
1. Staff requests reversal with reason.
2. Bot verifies action is technically reversible.
3. Warning: marks reversed; timeout: removes timeout then reverses; ban: unbans then reverses.
4. Kick and purge cannot be reconstructed and are not auto-reversed.
5. Reversal is appended to case history.

/mod lock and /mod unlock:
1. Lock snapshots the previous bot-owned Send Messages state.
2. Bot applies locked state.
3. Unlock restores the exact saved state rather than guessed defaults.
4. Unrelated permission changes made by staff while locked are not trampled.

/mod slowmode:
- Sets channel slowmode after capability/channel validation and audits it.

/mod staff-alert:
- Creates a non-punitive internal flag for staff attention; it is not itself discipline.

/mod modstats:
- Shows operational moderation totals for a period; it is not a punitive staff leaderboard.

60. QUARANTINE, EVIDENCE, AND APPEALS
======================================================================

/mod quarantine flow:
1. Staff selects a message.
2. Bot captures bounded surrounding context needed to understand the incident.
3. Public message is deleted when Discord allows it.
4. Restricted evidence is stored for authorized staff; current implementation uses encrypted retained evidence.
5. Evidence content is retained 30 days by default, then content is purged while non-content audit metadata may remain.
6. Quarantine/case is logged.

Request Review / appeal flow:
1. Eligible moderation notice exposes Request Review.
2. Subject requests review for their own case.
3. Case transitions to appealed while temporary action clocks continue running.
4. Appeal routes to staff review.
5. Original acting moderator may provide context but cannot be sole reviewer of their own action.
6. Reviewer chooses Uphold, Modify, or Reverse and provides rationale.
7. Modify applies supported changes, such as adjusted timeout/ban duration, when technically valid.
8. Reverse safely undoes reversible actions.
9. Outcome/rationale appends to permanent case history.

61. AUTO PURGE / CHANNEL CLEANUP
======================================================================

Dashboard feature: Moderation -> Cleanup -> Auto Purge
Default: disabled until a rule exists and is enabled.

Flow:
1. Admin creates per-channel cleanup rule.
2. Rule may set retention age, run interval, max messages per pass, bot/webhook exclusion, excluded members/roles, and supported content filters.
3. Pinned messages are always excluded.
4. Scheduled job wakes at rule interval.
5. Bot finds eligible old messages within safe Discord API constraints.
6. Messages are deleted up to the pass limit.
7. If anything was deleted, one summarized cleanup audit/log entry is written.
8. Auto Purge does not create a moderation case for every deleted housekeeping message.
9. Partial/failure is recorded and retried at the next scheduled run, not in an aggressive loop.
10. Execution is restart-safe/idempotent.

62. AUTOMOD
======================================================================

Passive moderation feature.

Flow:
1. New message/event enters deterministic filter evaluation.
2. Configured exemptions/trusted domains/users/roles/channels are applied where appropriate.
3. Filters may detect repeated spam, flooding, duplicate text, excessive caps/newlines/emoji/stickers/attachments/mentions, invite/general links, phishing/malicious URLs, masked links, shorteners, banned phrases, protected-class hate/slurs, Unicode/Zalgo obfuscation, spoiler abuse, oversized-message abuse, and detectable webhook/bot spam patterns.
4. Obvious deterministic matches follow their configured action path.
5. AI review is used only after a relevant trigger when context is genuinely ambiguous; the system does not AI-classify every message.
6. Action may be log only, warn, delete, quarantine/review, timeout, or progressive-discipline escalation.
7. Serious interventions create/link a moderation case and staff log.
8. Member notification/appeal path is provided when appropriate.

======================================================================
63. PROGRESSIVE DISCIPLINE / BEHAVIOR HEAT
======================================================================

Flow:
1. Relevant moderation events add configured bounded weight to recent behavior score.
2. Score decays over time.
3. Repeated similar violations may escalate faster.
4. Staff can inspect why the score is elevated.
5. Score alone never causes punishment; enforcement requires configured threshold plus rule context.
6. Severe incidents may skip low stages.
7. Default conceptual path: log/soft warning -> warning -> short timeout -> longer timeout -> staff review/restricted state -> kick/ban when configured/approved.
8. Authorized staff may adjust/clear with audit trail.

======================================================================
64. JOIN GATE AND VERIFICATION
======================================================================

Passive new-member security.

Join Gate flow:
1. Member joins.
2. Bot evaluates configured risk signals such as account age, join velocity, suspicious/default-profile patterns, suspicious names, immediate scam patterns, unauthorized bot additions, join/leave cycling, and prior case history.
3. An alt account is not automatically treated as wrongdoing.
4. Depending on confidence/config, member is allowed, flagged, required to verify, temporarily restricted, first-message quarantined, or rejected/kicked only under configured high-confidence rules.
5. Staff/security logs update.

Verification flow:
1. If verification is required, member receives a simple interaction/button challenge by default.
2. Verification state is persisted.
3. Successful verification clears the configured restriction and onboarding continues.
4. Failure/timeout follows configured restricted-state policy.
5. No unnecessary personal identity information is collected.

======================================================================
65. ANTI-RAID
======================================================================

Flow:
1. Bot continuously evaluates raid signals: join velocity, clusters of young accounts, repeated messages, mass mentions, invite/link spam, channel flooding, and many new accounts triggering the same serious rule.
2. Security state begins at Normal.
3. Threshold crossing can escalate to Alert: staff warning + enhanced logging.
4. Further threshold can escalate to Restricted: tighter new-member limits/verification.
5. Severe/continued threshold can escalate to Lockdown: temporary emergency restrictions.
6. State changes are logged/cased where appropriate.
7. Authorized staff may manually enter/leave states.
8. Automatic de-escalation follows configured thresholds/timers.

======================================================================
66. ANTI-NUKE
======================================================================

Flow:
1. Bot monitors Discord events/audit-log data for destructive privileged actions.
2. Signals include mass channel/role create/delete, repeated kicks/bans, dangerous permission escalation, webhook abuse, unauthorized bot additions, large-scale permission changes, server configuration changes, and mass role changes.
3. Holding a staff role does not automatically exempt an actor from monitoring.
4. Explicit trusted identities may be configured, but destructive monitoring remains active.
5. On dangerous activity, bot can immediately alert staff and create an emergency case.
6. Within Discord role/permission limits it may remove dangerous roles/permissions, quarantine/restrict actor, enter Restricted/Lockdown, and disable vulnerable bot-admin features.
7. Bot records what it actually changed and never pretends it can undo Discord actions that already occurred.
8. Recovery helpers use saved known state where possible.

Throne-only activation by default.

4. Any restoration issues are surfaced/audited.
5. Deactivation is audited.

68. MODERATION HOTSEAT
======================================================================

Commands: /jail send, release, extend, reduce, reason, history, roster, status
Moderation jail is separate from crime jail.
Default role: Jailed. Default channel: hotseat.

/jail send flow:
1. Staff chooses member, duration, and reason.
2. Duration supports 5 minutes-30 days plus indefinite manual release.
3. Bot validates moderator authority, target protection, hierarchy, Administrator bypass, and whether confinement can actually work.
4. Normal role-only jail is refused for a member who still has Administrator unless the separately enabled Throne-only staff-role suspension path can safely remove that bypass.
5. Bot creates/links numbered JAIL moderation case.
6. Bot snapshots only role/access data needed for safe restoration.
7. Jailed role and configured safe suspensions are applied.
8. Active wager/game participation that could bypass confinement is canceled/blocked and safely refunded/settled according to the originating system.
9. Bot verifies effective containment before claiming success.
10. Jail-entry card posts in Hotseat with member, reason, sentence, case ID, release time, and allowed controls.
11. Private explanation is attempted when DMs are allowed.
12. Action logs to staff channel.
13. Expiry job is persisted and restart-safe for finite sentences.

While moderation-jailed:
- Allowed: /jail status, /jail reason, /rules, limited /help, Request Review, and configured Hotseat text/reactions.
- Blocked by default: economy, gambling, games, social, music controls, custom commands, family, transfer, gifting, shop, crafting, robbery, Race/Fight, and ordinary community commands.
- Passive receipts already in motion may settle safely.

Extend/reduce flow:
1. Staff invokes /jail extend or /jail reduce with reason.
2. Bot checks capability and active sentence.
3. New remaining/end state is calculated within hard bounds.
4. Persisted expiry job is updated idempotently.
5. Same case receives an audit transition.
6. Public/staff/member card/state updates.

Release flow:
1. Release can occur by expiry, /jail release, successful appeal/reversal, or case modification.
2. Bot removes only restrictions it owns.
3. Only explicitly suspended roles are considered for restoration.
4. Unrelated role changes made while jailed are preserved.
5. If database transition fails mid-release, Discord state is rolled back where needed so the bot does not accidentally free an active sentence.
6. Role restoration failures do not block sentence closure when safe.
7. Normal member access restoration occurs only when no active jail/punishment state remains.
8. Crime jail is not cleared by moderation release.

Leave/rejoin while jailed:
1. Sentence persists.
2. Finite sentence pauses while absent under the current rejoin contract.
3. On return, member acknowledges rules.
4. Remaining moderation jail is reapplied/resumed rather than granting normal access.

/jail roster labels CRIME, MODERATION, or BOTH.
Bail never clears moderation jail.

3. Admin opens a settings page.

5. Shared ConfigService validates it.

7. Every mutation records immutable audit entry with actor, timestamp, object/setting, old value, new value, and relevant Discord IDs.

High-impact Draft flow:
1. Admin makes a destructive, broad-member, high-impact, or dependency-sensitive change.
2. System requires Draft Mode.
3. Only one global shared draft exists at a time and may span multiple dashboard sections.
4. All Admins can view it, but only one Admin may edit at a time.
5. Edit lock auto-releases after 15 minutes inactivity.
6. Server owner may force-unlock/take over early; takeover is audited.
7. Admin runs Preview.
8. Preview groups changes by section and shows direct dependencies/affected objects/members where practical.
9. Broken direct dependencies block publication.
10. Bot does not auto-rewrite dependent settings; admin must resolve each flagged issue.
11. If any staged item fails validation, entire draft is blocked; no partial publish.
12. Any one authorized Admin may publish the valid draft; second approval is not required.
13. Draft publication cannot be scheduled.
14. Publish writes live configuration and immutable audit entries.

Rollback flow:
1. Admin selects retained configuration history.
2. System validates rollback safety/dependencies.
3. Rollback creates a new mutation/audit event; old history is never rewritten.
4. If a deleted Discord object must be recreated, a new Discord ID is expected and bot updates its mappings.
5. External references that cannot be safely repaired are flagged.

Audit retention:
- 365 days rolling by default.
- Admins may export retained history.
